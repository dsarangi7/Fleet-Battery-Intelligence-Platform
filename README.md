# Fleet Battery Intelligence Platform

Source repository: https://github.com/dsarangi7/Fleet-Battery-Intelligence-Platform

This is the designated repository for subsequent project updates. Validate changes,
commit them to `main`, and push to `origin`; keep generated data and local secrets
out of version control.

A runnable engineering portfolio project demonstrating Python ingestion, a SQL
analytical warehouse, hierarchical battery metrics, condition-matched anomaly
detection, scheduled batches, and a read-only API.

All telemetry is generated by an original deterministic simulation. No AYK
source code, private algorithms, customer records, internal documents, or real
asset identifiers are used. SYN identifiers refer only to simulated packs.

## Run locally

Requires Python 3.11 or later. Runtime and tests have no third-party dependencies.
From this directory:

```powershell
python -m fleet demo
python -m fleet serve
```

Open http://127.0.0.1:8080 for the interactive dashboard. The fleet overview shows
capacity trends, a review queue, pack metrics, cell-session evidence and quality
counts. Pack, time-window and session-status filters work on warehouse results.
Refresh reloads the data; failed refreshes label the previous snapshot as stale.
The JSON API index is at `/api`. Example endpoints:

- `/health`: warehouse readiness
- `/api/fleet_daily`: fleet rollup
- `/api/pack_daily`: pack metrics and cell voltage spread
- `/api/module_daily`: module hierarchy
- `/api/cell_metrics?limit=10000`: capacity, SOC, SOH, alerts and scoring status
- `/api/degradation`: observed SOH slopes
- `/api/quality_summary`: invalid, missing and unscored session coverage
- `/api/ingestion_runs`: file-level lineage and acceptance counts
- `/api/quality_issues`: rejected row numbers and sanitized reasons

Responses are JSON. Resource queries accept `limit=1..10000` (default 1000).
The API intentionally exposes only an allowlist of analytical resources.
It offers no write endpoint or arbitrary SQL endpoint.

```powershell
python -m unittest discover -s tests -v
python -m compileall -q fleet tests
python -m fleet ingest
python -m fleet schedule --interval 3600
python -m fleet report
```

The scheduler scans CSVs in `data/` every hour, immediately runs its first batch,
skips already processed file hashes, logs failures, and retries on the next tick.
Stop with Ctrl+C. Supply `--data PATH` and optionally `--db PATH` for a separate
demo warehouse. `demo` preserves an existing CSV. Use a new directory to generate
a clean independent run. Completed files are immutable; submit corrections into
a fresh warehouse, because conflicting existing samples are quarantined.

Generated files (ignored by Git):

- `data/synthetic.csv`: 45 days, six packs, 12 cells per pack, 11 samples per session
- `data/manifest.json`: seed, topology, simulation assumptions and fault injection
- `data/truth.json`: labels used only by offline evaluation
- `data/warehouse.sqlite`: source, lineage, quality evidence and SQL analytical marts
- `data/evaluation.json` and `data/RUN_REPORT.md`: reproducible measured results

## Docker deployment

With Docker Engine and Compose available:

```sh
docker compose up --build -d
docker compose ps
docker compose logs init scheduler
curl http://localhost:8080/health
docker compose down
```

The init job generates and loads the demo. API and scheduler start after it
succeeds, sharing a persistent named volume. Containers run as an unprivileged
user. The host port binds to loopback. `down` preserves the warehouse; `down -v`
deletes it. The container image uses only the Python standard library.

This is a local/container portfolio deployment. The standard-library HTTP server
is suitable for a controlled demo. Internet hosting requires a production HTTP
server or gateway, TLS, authentication, request limits, and operational monitoring.
SQLite is appropriate for the included batch size and one scheduler writer;
distributed ingestion requires a different coordination/storage design.
